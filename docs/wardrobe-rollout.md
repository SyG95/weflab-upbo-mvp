# 옷장 개편 — 로컬 구현, 배포 전 검증 필요

운영 기준 커밋: `157180ca9e5d215cb682418c8d7f296ab0607054`.
기존 작업 디렉터리 대신 별도 worktree에서 구현했다. 운영 데이터·스키마·배포는 변경하지 않았다.

## 변경 동작

- 신규 옷장은 테마·월·파츠를 비운 채 이미지만 등록한다.
- 월별·테마별·파츠별 팬 필터는 관리자 설정으로 선택한다. 미분류 이미지도 전체 보기에서 노출된다.
- 기존 옷장은 설정 필드가 없으면 종전 팬 화면과 업로드 기본값을 유지한다. 기존 항목을 일괄 변환할 필요가 없다.
- 기존 테마 ID, 항목 ID, 이미지 URL, 표시 순서, 색상 세트, 공개 여부, 최초 공개 시각을 유지한다. 중복 이미지를 합치지 않는다.
- 저장 revision 비교, 재시도 요청 ID, 세트의 부분 파츠 변경 방지, 저장 결과 불명확 시 이미지 보존을 추가했다.

## 로컬 검증

`npm ci`, `npm run test:wardrobe`, `npm run build`.
`tests/wardrobe-migration.mjs`는 별도 PGlite 0.3.14 런타임을 사용한다. `WARDROBE_PGLITE_MODULE`에 해당 모듈의 절대 경로를 지정하면 `node tests/wardrobe-migration.mjs`로 실행할 수 있다. 운영 접속 정보는 사용하지 않는다.

실데이터 비교 및 복구 실험은 저장 상태가 있는 14개 옷장으로 수행했다. 실제 데이터와 이미지 백업은 저장소 밖 로컬 작업 디렉터리에 보관하며 Git 또는 Vercel 업로드에 포함하지 않는다.

로컬 DB는 PGlite이며 PostgREST와 Storage는 제한된 로컬 HTTP 서버로 대체했다. 이 환경은 전체 Supabase, 운영 RLS, 별도 DB 연결 사이의 동시 트랜잭션, Vercel 런타임 검증을 대신하지 않는다.

## 배포 조건과 순서

1. 독립된 실제 PostgreSQL/Supabase 검증 환경에 운영의 관련 스키마·권한과 데이터 복사본을 준비한다. 운영 DB를 테스트 쓰기 대상으로 사용하지 않는다.
2. `20260909110936_wardrobe_atomic_save.sql`을 검증 환경에 적용한다. service_role RPC 저장, anon/authenticated 실행 거부, 독립 연결의 동시 저장, 구버전 요청 차단, 다른 audit_logs 작업, 업로드 실패·삭제·재시도를 검증한다.
3. Vercel 검증 배포를 위 검증 DB/Storage에 연결한다. 현재 운영 스키마·환경과의 차이를 확인하고 기존 팬 화면 및 관리자 전체 흐름을 검증한다. 로컬 `.env.local`이나 로컬 빌드 산출물을 운영 환경으로 재사용하지 않는다.
4. 배포 직전 실제 운영의 최신 스냅샷·파일과 코드 버전을 다시 확인하고 백업한다. 변경분이 있으면 비교를 다시 수행한다.
5. 검증한 추가 SQL을 먼저 적용하고 새 코드를 배포한다. 기존 옷장 스냅샷을 일괄 재작성하지 않는다. 특히 꾸야의 설정을 임의 변경하지 않는다.
6. 운영 공개 화면을 읽기 전용으로 비교한다. 저장 실패율·파일 오류·구버전 저장 거부가 발생하는지 확인한다.

SQL의 버전 보호 트리거는 새 형식이 저장된 옷장에 이전 서버가 구형 스냅샷을 덮어쓰는 것을 거부한다. 해당 요청은 새로고침 후 재시도가 필요할 수 있다. 데이터 유실을 막는 장치이며 사용자 영향이 절대 없다는 보장은 아니다.

## 복구

- 새 형식 데이터가 저장된 이후에는 구버전 코드로 단순 롤백하지 않는다. 구버전은 미분류 파츠와 새 설정을 해석하지 못한다.
- 새 데이터를 읽고 보존하는 호환 코드에서 표시 설정을 복구한다. 이미지·분류·세트를 보존한 복구를 검증해야 한다.
- 과거 스냅샷을 현재 값으로 덮어쓰면 그 이후의 사용자 변경을 잃는다. 최신 revision을 확인한 상태에서 필요한 변경만 적용한다.
- audit_logs는 파일 백업이 아니다. 업로드 파일 백업과 해시 목록을 함께 보존한다. 저장 결과가 불명확한 업로드 파일은 참조 여부를 확인하기 전 삭제하지 않는다.

이 문서 작성 시점에는 위 배포 조건 1~3이 충족되지 않아 운영 배포를 보류했다.

## 추가 비용 없는 후속 검증

후속 검증에서 정식 PostgreSQL 17.6 및 PostgREST 16.2를 로컬에서 실행하고 운영 두 테이블의 컬럼·제약·RLS를 재현했다. Node.js 24.20.0 빌드, 권한·DB 검사 12건(실제 별도 연결의 잠금 경합 포함), 앱 API 15건, 실패 주입 6건, 기존 옷장 14개 복구, 꾸야 15개 월·테마 브라우저 비교를 통과했다. 기존 HTML 비교 271건과 회귀 22건도 통과했다.

Storage는 로컬 파일 대체 서버이므로 관리형 Supabase Storage와 Vercel 호스팅 통합까지 완료된 것은 아니다. 운영 배포는 보류 상태이며 유료 브랜치는 만들지 않았다. 앱 코드에는 추가 수정이 없었다.

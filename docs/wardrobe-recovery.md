# 옷장 긴급 복구 실행 절차

이 문서는 **준비된 절차**다. 작성 과정에서 운영 저장 차단, 환경변수 변경, 배포, 데이터 복구를 실행하지 않았다.

## 복구 원칙

최신 데이터는 그대로 보존한다. 과거 스냅샷으로 전체를 덮어쓰거나, 새 형식을 읽지 못하는 이전 배포로 즉시 되돌리지 않는다. 옷장만 저장을 멈추고, 최신 공개 이미지를 읽는 호환 화면으로 전환한 뒤 원인을 수정한다.

정상 배포에는 `UPBO_WARDROBE_RECOVERY`를 설정하지 않는다. `read-only`일 때만 다음 동작을 한다.

- 인증된 옷장 수정·업로드 요청에 파일 처리 전 HTTP 503을 반환한다.
- 관리자 옷장 편집기를 점검 안내로 대체한다.
- 팬 화면에서 최신 공개 원본을 서버 렌더링으로 보여준다. 미분류와 색상 세트의 각 이미지도 모두 보이며 숨김 이미지는 제외한다.
- 테마·월·세트·순서·공개 상태·파일을 수정하지 않는다. 점검 중에는 검색·필터·세트 접기 등의 기능이 잠시 제공되지 않는다.

임시 보기 역시 DB 조회와 이미지 저장소가 정상이어야 한다. DB 자체 장애를 우회하는 기능은 아니다. 원본을 직접 표시하므로 평소 썸네일 화면보다 전송량이 늘 수 있다.

## 배포 전에 준비할 것

1. 현재 운영 배포 ID·소스 커밋·환경 설정을 기록한다. 마지막 확인 기준은 배포 `dpl_GFGTn7R4W71X8g1mteLvb4KovASt`, 커밋 `157180ca9e5d215cb682418c8d7f296ab0607054`이며 배포 직전 다시 확인한다.
2. `ops/wardrobe/snapshot.sql`을 읽기 전용으로 실행해 반환된 `snapshot` 객체를 별도 로컬 JSON으로 저장한다. 이는 한 SQL 문장의 일관된 최신 스냅샷이다. 관리자 비밀번호는 포함하지 않는다.
3. 이 스냅샷이 참조하는 원본·썸네일 파일을 백업하고 파일 경로·바이트 수·SHA-256 목록을 보관한다. 현재 준비된 456개 백업은 조사 시점의 자료다. 이후 신규 파일은 배포 직전 다시 백업해야 한다.
4. 백업·환경 파일은 권한을 제한하고 Git/Vercel 업로드 밖에 보관한다. 옛 audit 로그만으로 삭제된 파일을 복구할 수 있다고 가정하지 않는다.
5. 본 복구 모드가 들어간 소스 커밋과 Node.js 24 빌드 성공을 기록한다. 현재는 로컬 빌드만 준비되어 있고 미리 배포된 클라우드 복구 URL은 없다. 필요 시 빌드·배포 시간이 든다.

## 중단 기준

다음 중 하나가 확인되면 추가 편집을 허용한 채 조사하지 말고 옷장 저장부터 멈춘다: 이미지·분류·세트 유실, 숨김 이미지 공개, 잘못된 스트리머 데이터 노출, 최신 수정 덮어쓰기, 반복되는 저장/파일 오류. 꾸야의 데이터나 표시가 예상과 다르게 바뀐 경우도 포함한다.

## 1. 구버전까지 포함해 저장 차단

DB 소유자 권한으로 `ops/wardrobe/freeze.sql`을 실행한다. 이 SQL은 기존·신규 모든 서버의 `wardrobe_updated` INSERT를 막는다. 다른 audit 작업과 조회는 그대로 유지한다. 기존 버전 보호 트리거와 저장 RPC는 삭제하지 않는다.

`ops/wardrobe/status.sql` 결과에서 `writes_frozen=true`를 반드시 확인한다. 잠금 대기 5초·실행 15초 제한을 두었으므로 시간 초과가 나면 성공으로 간주하지 않는다. 실패한 트랜잭션은 ROLLBACK하고 상태를 다시 확인한다. 자동으로 제한을 무한히 늘리지 않는다.

DB 차단은 이미 진행 중인 Storage 요청을 취소하지 않는다. 진행 중 요청과 로그를 확인한 후 스냅샷과 파일 상태를 다시 수집한다. 차단 이후 생긴 고립 업로드 파일을 임의 삭제하지 않는다.

## 2. 호환 임시 보기로 전환

본 코드가 포함된 검증된 소스에서 운영 프로젝트로 배포하면서 런타임 환경변수 `UPBO_WARDROBE_RECOVERY=read-only`를 지정한다. 다른 환경변수는 기존 운영 값을 유지한다. 로컬 DB URL·로컬 PIN·로컬 `.env.local`을 사용하지 않는다.

Vercel CLI에서 지원 여부를 확인한 준비 명령은 다음과 같다. **실행하면 운영 배포를 만드는 명령이며 아직 실행하지 않았다.** 운영 프로젝트에 연결된 깨끗한 소스에서만 실행한다.

```sh
vercel deploy --prod --env UPBO_WARDROBE_RECOVERY=read-only
```

배포 후 확인한다: 공개 팬 화면이 200이고 점검 안내가 나오는지, 숨김 이미지가 없는지, 신규 미분류 이미지가 보이는지, 인증된 옷장 POST가 503인지. 옛 탭·옛 서버 요청은 DB 차단이 계속 보호한다.

현재 DB·이미지 상태를 새 이름으로 다시 백업한다. 배포 전 백업과 사고 시점 백업을 섞거나 덮어쓰지 않는다.

## 3. 필요한 부분만 복구

- **화면 문제:** 최신 데이터를 그대로 두고 호환 코드의 원인을 수정한다. 꾸야 설정을 일괄 변경하지 않는다.
- **데이터 문제:** 사고 전후 ID·항목·테마·세트별 차이를 먼저 검토한다. 정상적인 신규 등록·수정·삭제까지 되돌리지 않는다. 복구할 필드와 대상이 특정되기 전에는 스냅샷 덮어쓰기를 실행하지 않는다. DB 동결 중 복구 INSERT도 막히므로, 데이터 수정이 필요하면 별도의 검토된 SQL·트랜잭션 계획이 필요하다. 이 절차에는 포괄적인 데이터 덮어쓰기 도구를 포함하지 않았다.
- **파일 누락:** 현재 스냅샷이 참조하는 파일만 복구한다. 아래 도구는 기본적으로 계획만 출력한다.

```sh
node ops/wardrobe/restore-assets.mjs \
  --snapshot CURRENT_SNAPSHOT_JSON \
  --manifest BACKUP_MANIFEST_JSON \
  --backup-dir BACKUP_DIRECTORY \
  --origin https://qigsltckwwvlxudktubp.supabase.co
```

`CURRENT_SNAPSHOT_JSON`은 `snapshot.sql` 결과의 snapshot 객체다. manifest는 `{path,bytes,sha256}` 객체 배열이며 path는 `wardrobe/슬러그/파일명`이다.

오류가 없고 대상 파일 목록을 검토한 후에만 안전한 실행 환경에 `WARDROBE_RESTORE_SERVICE_KEY`를 설정하고, DB 동결을 직접 확인했다는 의미로 `WARDROBE_WRITES_FROZEN=1`을 설정한 뒤 같은 명령에 `--apply`를 붙인다. 환경변수 값이나 토큰을 로그에 출력하지 않는다.

도구는 HTTP 404인 현재 참조 파일만 백업 해시를 검사해 업로드하고 다시 다운로드해 검증한다. `x-upsert=false`로 기존 파일 덮어쓰기를 금지한다. 401·403·5xx는 파일 누락으로 취급하지 않는다. 과거 로그에만 있는 파일은 복구하지 않는다. 백업이 없거나 해시가 다르면 멈춘다. 서비스 장애나 동시 생성으로 실패하면 새 계획부터 다시 확인한다.

## 4. 정상 운영으로 복귀

1. 데이터·참조 파일·숨김 여부·꾸야 구성을 검증한다. 신규 미분류 이미지도 포함한다.
2. DB 동결을 유지한 채 수정된 정상 코드를 배포한다. `UPBO_WARDROBE_RECOVERY`를 제거하거나 이 배포에서 `off`로 지정한다. 정상 팬 화면을 읽기 전용으로 확인한다.
3. 옛 서버의 진행 중 저장 요청이 없는지 확인하고 `ops/wardrobe/unfreeze.sql`을 실행한다. 이것은 긴급 차단만 제거하며 CAS RPC와 버전 보호는 남긴다.
4. `status.sql`에서 동결 해제·버전 보호·RPC 존재를 확인한다. 운영 저장 확인은 별도의 테스트 대상에서 수행하며 꾸야 데이터로 시험하지 않는다. 잠시 뒤 파일 오류·저장 오류·충돌을 다시 확인한다.
5. 문제가 재발하면 1단계의 DB 동결로 돌아간다. 과거 전체 백업을 덮어쓰는 방식으로 대응하지 않는다.

## 실제 연습 결과와 한계

로컬 실제 PostgreSQL에서 동결·구/신버전 차단·다른 기록 유지·해제·정상 저장 재개 8건을 통과했다. 복구 모드 앱에서 꾸야·숨김 이미지가 있는 계정·신규 미분류 계정의 공개 이미지 및 저장 차단 6건을 통과했다. 파일 복구 도구의 계획만 실행, 누락 복구, 숨김 참조 보존, 과거 파일 제외, 재실행, 해시 오류·5xx 차단을 6건으로 검증했다. 회귀 테스트 25건과 Node.js 24 빌드도 통과했다.

Vercel 운영 배포/전환과 Supabase Storage 실제 복원은 실행하지 않았다. DB가 내려간 상황, 백업 자체가 없는 파일, 사람의 확인이 필요한 데이터 충돌은 이 자동화만으로 복구할 수 없다.

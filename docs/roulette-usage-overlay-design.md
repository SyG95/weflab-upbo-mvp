# 룰렛확률표 사용여부(on/off) 오버레이 — 설계안

작성: 2026-07-02 · 상태: **sy 승인 대기** · 구현 전 문서

## 1. 목표

위플랩 캡처(원본)는 지금처럼 불변의 증거로 보관하고, 그 위에 **"이 상품/룰렛을 우리 사이트가 쓸지 말지"를 sy가 직접 결정하는 오버레이(덮개) 층**을 만든다. 위플랩 = 원본 데이터 공급자, 운영 결정권 = 업보사이트. 상품 내용·확률의 수정/추가는 이 설계의 범위가 아니다(기존과 동일하게 캡처가 내용의 기준).

## 2. 확정된 설계 결정 (2026-07-02 sy 확정)

1. **내 설정이 최종 결정권.** 위플랩 캡처의 활성화 값은 "기본값 + 참고 표시"로만 쓴다. 내가 설정하지 않은 상품은 위플랩 값을 그대로 따른다.
2. **내용이 완벽히 일치하지 않는 룰렛표는 각각 별개의 독립 룰렛.** 같은 33/330개 후원 구간이라도 내부 상품·확률이 바뀌면 새 캡처 버전 = 새 룰렛으로 간주한다. 설정의 자동 승계는 없다. 대신 "이전 표에서 내 설정 가져오기" 버튼(명시적 복사)과 이전 표 대비 변경점 하이라이트를 제공한다.
3. **내용 수정·상품 추가는 범위 밖.** 기존에도 캡처된 표가 기준이었으므로 새로운 제약이 아니다. 향후 필요해지면 "풀 운영표"로 확장하며, 이 오버레이는 그 1단계로 재사용된다.

## 3. 데이터 구조 — 스키마 변경 없음

기존 audit_logs 재활용(쇼케이스·뷰어노트·두배권 예외룰과 동일 패턴).

- action: `"catalog_usage_updated"`
- payload 예시:

```json
{
  "catalogVersion": 7,
  "overrides": {
    "g0-i2": false,
    "g1-i0": true
  }
}
```

- **키는 버전 내부 인덱스**(`g{그룹번호}-i{상품번호}`). 결정 2에 따라 설정이 특정 캡처 버전에 고정되므로, 버전 안에서는 인덱스가 유일하고 모호함이 없다(같은 상품명+확률 중복 문제 원천 차단 — 교환 드롭다운에서 이미 검증된 방식).
- append-only: 저장할 때마다 새 기록. **(스트리머, catalogVersion)별 최신 1건이 현재 상태.** 과거 시점 재현은 그 시점 이전의 최신 기록을 읽으면 된다(판정 재현성 보장).
- 그룹(룰렛 단위) on/off도 같은 payload에 `"g0": false` 형태로 지원.

## 4. 판정 파이프라인 연결 — 판정 엔진 무수정

- 불가침: `reconcileResults()` 로직은 한 줄도 수정하지 않는다.
- 현재 파이프라인은 이미 `enabled !== false` 상품을 걸러서 판정에 넣는다(upboCore). 오버레이는 **판정 엔진에 표를 먹이기 직전에** 적용한다:

```text
효과적 enabled = 내 오버라이드가 있으면 그 값, 없으면 위플랩 캡처 값
```

- 내가 끈 상품의 당첨은 위플랩에서 꺼진 상품과 **완전히 동일한 기존 경로**로 처리된다(새 판정 유형을 만들지 않음).
- 새 판정부터 적용. 기존 판정 기록은 불변. 검증실의 "원본 재현" 경로는 원본 스냅샷 + 당시 오버레이 상태로 재현.
- **안전망 검증**: 오버라이드가 하나도 없을 때 판정 결과가 기존과 100% 동일해야 한다(회귀 기준).

## 5. 관리 화면 — CatalogManager 승격

현재 "읽기 전용 참고 화면"인 확률표 탭에 추가:

- 상품/그룹별 **사용 on/off 토글** + 위플랩 원본 상태 배지(예: "위플랩에선 꺼짐")
- 새 캡처 버전 진입 시: "이전 표에서 내 설정 가져오기" 버튼 + **이전 표 대비 변경점 하이라이트**(추가/삭제/확률변경)
- 저장: 기존 extension 토큰 인증, 단계별 진행 문구("저장 중… → 적용됐어요!") — 쇼케이스와 동일 UX
- API: `POST /api/s/[slug]/catalog-usage` (theme/showcase 라우트와 동일 인증 패턴)

## 6. 구현 단계 (승인 후)

1. **데이터+API**: getCatalogUsage/setCatalogUsage + 라우트 (audit_logs 패턴)
2. **판정 연결**: 표 공급 지점에 오버레이 적용 + "오버라이드 0개 = 기존과 동일" 회귀 검증
3. **관리 UI**: 토글/배지/가져오기/변경점 표시
4. **검증**: tsc/lint/build + 임시 QA 페이지(레이아웃) + production 배포 후 실데이터 확인

## 7. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 판정 결과가 의도치 않게 변함 | 오버라이드 없으면 기존과 100% 동일 회귀 검증을 통과해야 배포 |
| 표 바뀔 때마다 설정 백지화 | 기본값=위플랩 값 + 명시적 "가져오기" 버튼 + 변경점 표시 |
| 과거 판정 재현 불가 | append-only 기록으로 시점별 상태 복원 가능 |
| core/스키마 침범 | reconcileResults 무수정, DB 스키마 변경 없음 |

## 8. 건드리지 않는 것

Chrome 확장 수집, 위플랩 캡처 저장 구조, raw_imports, reconcileResults 로직, DB 스키마, 인증 구조, 기존 판정 기록.
